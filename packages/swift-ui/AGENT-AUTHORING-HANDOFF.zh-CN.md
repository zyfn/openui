# Intelligent UI 与 OpenUI Lang：服务端生成指引分析材料

这份材料汇总 SDK／用例打磨过程中实际发生的失败，供服务端审视现有 Prompt 与 Skill。它是分析输入，不应整篇复制进系统提示词，也不新增语法、样式参数或业务协议。能力与参数始终以客户端实际导出的 Lang／LibrarySpec 为准。

## 1. 先建立正确的输出定位

**Intelligent UI 是 Assistant Message 的一种内容呈现方式：让用户在消息中阅读、理解、比较和操作一页内容。OpenUI Lang 是描述这页内容、布局、状态与动作的语法。**

- Intelligent UI 负责表达：回应什么问题、先解释什么、如何组织证据、哪里需要交互。
- OpenUI Lang 负责声明：用实际注册的组件、参数、引用、绑定和动作，把表达落成可渲染内容。
- SDK 负责呈现：主题、几何、控件状态、资源、增量渲染和事件生成。
- 客户端宿主负责消息承载、流式数据传入、资源策略、事件回传、导航和真实执行。
- 服务端／Agent 负责事实来源、内容组织、组件选择、状态表达和下一步意图。

一页内容可以纯阅读，也可以包含局部交互；“可交互”不意味着每次必须给用户表单。短答可以很轻，复杂回复可以展开。它不是要求 Agent 创建独立 App、后台控制台或一套新导航。

页面作为当前 Assistant Message 的正文交付，遵守现有客户端识别的围栏／消息格式。不要另用发送消息工具绕过正文通道，不把 DSL 源码、解析诊断或持久化标记作为用户需要理解的界面。SDK 的 buildMessage／parseMessage 是宿主消息能力，不应由模型临时发明另一套编码。

## 2. 以阅读关系选结构，不以组件清单拼页面

先判断本轮要帮助用户完成什么：了解、比较、选择、调整条件、执行，还是继续讨论。再组织“主要回答 → 判断依据 → 必要细节 → 有意义的操作”。不强制每条消息都有封面、地图、图表、卡片、表单和后续问题。

普通店铺知识清单可以由标题、简短说明、图文行或列表组成，留白已经能表达分组。没有独立对象边界或局部操作时，不必一店一框。完整商品、可比较候选、填写并提交的任务则需要清楚的对象／操作边界。

同类对象内部保持一致，章节之间按内容调整密度。多轮回复承接已有条件，回答本轮新增问题，不反复重写整页。

## 3. 应由生成指引控制的已知问题

| 实际问题 | 应收口的原则 |
| --- | --- |
| 普通知识也被拆成一堆独立卡片，消息像后台 | 以信息关系组织；Card 表示独立对象或操作单元，不代替普通段落、章节和列表。不要再给专用卡片组套一层通用 Card。 |
| 为了边框把商品卡套进 Form | Form 的依据是收集用户值并统一提交；纯展示、直接打开详情／预订链接不需要 Form。即时筛选可以只使用本地状态。 |
| 单商品写成 CompositeCardBlock([one]) | 服从 items 至少两项的实际契约；单对象使用合法的 Card 组合，不为凑数虚构第二个商品。数据 Item 不当成任意容器自由嵌套。 |
| 任意内容都再包一层 Stack，列宽失去预期 | 容器有明确职责；不要机械包装。需要共享宽度的 Card 应直接成为横排子项。wrap 仅表示允许换行，不等于所有子项自动等宽、自动撑满。 |
| 手机多列被强行改成单列，或向 DSL 写不存在的列数参数 | 按表达关系使用既有 row、wrap、responsive、图库或卡片组；实际宽度适配由 SDK 负责，不创造 columns、CSS、像素宽度等未注册字段。 |
| 布局参数最后才到，流式过程中结构难稳定 | 在固定的位置参数语法内，优先声明 root、章节／容器骨架，再补叶子内容。可用前向引用先交代排列与集合形状；不强制每句纯文本都拆变量。 |
| 店名、描述、推荐理由、规格互相重复 | 名称负责识别，介绍提供有效信息，规格说明适用条件，推荐理由说明判断。简短卡内文字选紧凑角色，连续讲解用正文角色。 |
| 地址包含数字，就被当成数字值 | 地址、说明、条件仍是文字角色；金额／数量／时刻等使用对应数字角色。不要仅因字符串含数字就设置 number，影响换行和可读性。 |
| 标题、店铺、套餐名称被擅自润色或加卖点 | 工具返回的身份字段忠实展示；缺失允许省略。不能把自己的推荐理由冒充原商品描述，也不能补造权益、等级或库存。 |
| 票种、单晚／总价、起价、人数散落又重复 | 价格与口径就近；票种等简短条件放价格说明或明确规格位置。同一事实不在 Tag、正文、价格说明重复三遍。计算值须注明基于哪些返回值推算。 |
| 卡片外有价格或链接，卡内反而没有入口 | 交易对象卡内应有对应价格、适用条件与真实入口；比较表只能补充，不能替代对象卡的价格与动作。 |
| 查看、查询、预订文案与链接目标不符 | 使用工具返回的有效 URL，保留签名和查询参数。价格公示页不能包装为有库存的预订入口；实际去向决定动作文字。 |
| 图片 src 被写成 Markdown 链接字符串 | src 填原始资源地址，不写成 `[地址](地址)`；保留原地址、签名参数及对应对象关系，不替换成另一对象的漂亮图片。 |
| 希望通过换图片／改裁切补全关键商品信息 | 按组件既有图片角色组织。必须让用户读懂的价格与条件应有结构化文字，不能只存在于海报图片内，也不能依赖用户点预览才发现关键条件。 |
| 图标被随机赋予蓝、绿、棕等语义色 | 普通属性用中性样式；成功、警告、错误等状态色必须有状态依据。图标名称不意味着状态，不为百年老店、地址等静态属性随意染语义色。 |
| 到处塞 Tag 或把完整前提塞进 Tag | Tag 放有依据的短属性、差异或状态；长条件留在说明中。不为“丰富界面”造属性，不重复标题和价格已有信息。 |
| 所有按钮都 large／铺满，抢过内容 | 重要性、尺寸、排列分别决定；卡内入口使用正常紧凑档位，独立主操作才强调。用合法 Buttons(column) 等布局表达通栏，不新增 fullWidth 参数。 |
| 选择项与提交按钮分散，点击后不明确做什么 | 需要统一提交的字段和主按钮属于同一 Form；name／value／绑定保持对应，label 说清下一步。不能让模型假定客户端自动把表单值发给 Agent。 |
| 按钮之后的回答出现 demo／测试／示例话术 | 示例教表达方法，后续内容应像真实对话承接用户选择；不能把演示标签或固定样本事实复制为新的查询结果。 |
| 没执行工具却显示“已保存／已支付／已下单” | 点击只是意图或事件；成功状态只能依据实际执行结果。普通背景说明与真正操作状态区分，重要错误提供可行动的信息。 |
| SDK／Agent 自行说“正在整理内容”、展示源码诊断 | 不猜测业务进度，不让用户承担解析排查；调试诊断在内部。真实未知、预算边界、开放条件仍应清楚说明，不能一概删掉事实限制。 |
| 章节前后堆满分割线 | 标题和留白已有层次时不机械叠线；线用于记录边界、连接关系等确有作用的位置。 |
| 为让图表好看而补零、造数、任意彩色强调 | 图形来自真实可确认数据；系列名、单位、时间范围与来源清楚。图表类型服务于比较、趋势、组成或关系；配色和默认视觉交给 SDK。 |
| 示例写法超出客户端实际注册库 | 组件名、参数顺序、类型、必填、槽位、数组基数、动作以本次实际 Lang 为准；跳过中间可选参数按契约留 null，不猜位置，不创造组件。 |
| 复用旧 Lang／示例／版本说明，出现互相矛盾的规则 | 每次接入绑定 SDK、实际导出契约与示例身份。生成库可能过滤渲染库中的组件；不要拿“SDK 能渲染”当作模型一定可以生成。 |

这些是问题到原则的映射，不是要求把每一条都变成一条常驻禁令。请服务端依据现有 Skill 去重合并，形成少量能迁移到不同内容的规则。

## 4. 不应交给提示词解决的事情

- 末尾相同快照／空分片导致 State 重置、图片重新淡入、横滑与纵滑识别冲突：属于 SDK 或宿主生命周期与交互实现。
- 字号、字重、颜色、图标几何、两栏文字换行、加载和预览：由组件职责与 SDK 统一呈现决定，模型不要硬编码另一套 token。
- 表单点击后的实际字段、对象上下文与动作回传：SDK 生成事件，客户端按现有消息协议承载，服务端消费；Prompt 不能替代链路实现。
- Markdown 中文兼容及复杂行内图片交互：后续由客户端统一分析处理，当前不实施。可记录现有能力边界；不要全局删除空格／星号、静默改原文，也不要把要求 Agent 移动标点当成渲染修复的唯一方案。
- 静态 parser 的 errors／unresolved／incomplete／orphaned 是内部证据，不等于布局、事实或业务执行的验收，也不能直接映射成用户侧“内容不完整”提示。

## 5. 建议的 Prompt／Skill 分层

| 层 | 应承担的内容 |
| --- | --- |
| 常驻定位 | Assistant Message 的输出定位、事实责任、交互与执行边界；少量稳定原则。 |
| intelligent-ui Skill 主文 | 如何从用户目标、材料和阅读关系组织可交互内容；能力入口与按需阅读路线。 |
| 组合参考 | 叙事、图文、比较、数据、输入反馈等关系；典型模式与取舍，不固化业务专属页面模板。 |
| 实际 OpenUI Lang | 客户端导出的权威语法和组件契约；保持版本、签名、类型、槽位、动作信息完整。 |
| 标准示例 | 使用标准 examples 接口，展示合法组合和数据组织。01—07 为当前核心材料，08 保留原稿但未纳入本轮交付验收。不要手抄两份维护。 |
| 内部生成检查 | 是否回答问题、事实对应、对象完整、组件合法、交互真实、有无多余分组；不把检查报告输出给用户。 |
| 运行时验证 | 用实际 parser／客户端／SDK 回放确认契约与效果；校验元数据不混进模型可见正文。 |

跨端的共同部分是语义与契约，不是强行让网页与 iOS 拥有相同像素外观。也不要把所有组件、全部参考和历史问题重复塞进每轮 system prompt。

## 6. 请服务端交付的分析

1. 核对现有主提示、Skill、组合指南、Lang 与示例中有哪些重复、冲突和错误定位，给出具体位置。
2. 把上述失败归并为最少的表达原则，说明哪些常驻、哪些按需加载、哪些只留内部校验；不要原样复制本表。
3. 说明一条普通回复怎样成为可阅读、可操作的 Assistant Message；何时保持轻量、何时展开，而不把所有输出逼成表单或卡片墙。
4. 给出对现有 Skill 的可审阅改造方案，再按当前授权范围实施；不要顺带切换模型、扩大工具、修改协议或自动部署服务。
5. 用已有原始程序与当前实际契约做离线回归，并设计少量覆盖表达选择的真实生成验证：纯知识列表、单对象商品、带条件价格、多列图文、表单取消后提交、图表缺值与流式输出。

语法通过不能代替内容和视觉判断。最终应同时检查：模型输出是否满足用户目标、数据是否有依据、页面是否自然、事件是否按当前值与正确对象进入下一步。
